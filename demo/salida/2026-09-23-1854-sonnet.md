`intersect` is stored (hash `21fdac9bcd59`), but only at level 1 (examples passed). The prover did not close it.

**What I wrote.** `intersect` recurses on `xs`. It keeps the head `h` when `contains_in(ys, h)` is true and prepends it to the recursive result. Otherwise it drops `h`. It reuses `contains_in` from the store, which I read only through `sello_sig`. `sello_deps` lists `contains_in` (`cebf92985dd7`) as its only dependency.

**Contract.**
- `requires len(xs) >= 0`. The language wants a non-trivial `requires`, and nothing else is assumed.
- `len(result) <= len(xs)`.
- Every element of `result` is in `xs` and in `ys`.
- For each `x` in `xs` that is in `ys`, `count(result, x) == count(xs, x)`, so repetitions are kept.
- For each `x` in `xs` that is not in `ys`, `count(result, x) == 0`.

Order is not stated in the contract. It is covered only by the examples, for instance `[3, 1, 3]` with `[1, 3]` gives `[3, 1, 3]`. There are 5 examples in total, and all pass.

**`sello_check` calls.** 3 in total.
1. E000 syntax error: I left a placeholder token (`implies_placeholder`) in an `ensures` clause. That was my mistake, and the spec says there is no `implies`.
2. Accepted at level 1, with `unproven: "timeout: the solver did not answer"`.
3. I tried a lighter contract, ending in `contains(ys, x) == contains(result, x)`, to help the prover. It hit the same timeout.

I stored the stronger contract from call 2, since both versions ended at the same level.

**Obligation that failed.** I don't know which one it is, because the timeout message doesn't say. The likely cause is that the recursive step has to relate `count` and `contains` across `[h] ++ intersect(t, ys)` for the quantified clauses. It also relies on `contains_in` being certified only at level 1, and the prover uses its contract without re-checking its body.

**Certificate level.** 1, with 5 examples.
